# 규제 요구가 설계에 주는 제약

의료·개인정보 법령이 데이터 모델과 API에 직접 영향을 주는 부분만 정리했습니다. 법률 자문이 아니며, **구현 전에 국가법령정보센터 원문과 보건복지부 고시를 다시 확인해야 합니다.** 조문 번호와 기간 중 아래에서 "(확인 필요)"로 표시한 것은 이 문서를 쓰면서 원문으로 확인하지 못한 값입니다.

## 진료기록 정정

- **근거:** 의료법 제22조(진료기록부 등), 제23조(전자의무기록). 제23조제4항은 전자의무기록을 추가기재·수정하면 접속기록을 별도로 보관하도록 정하고, 추가기재·수정 전 원본도 함께 보존해야 한다고 알려져 있습니다
- **설계 반영**
  - 완료된 진료는 덮어쓰지 않고 버전을 쌓습니다 ([clinical.md](clinical.md#진료-encounter)의 `:amend`). 완료할 때 1판, 정정할 때마다 다음 판에 그때 내용 전체와 `recordedBy`, `recordedAt`, `reason`, `source`(지금은 완료 `COMPLETION`·정정 `AMENDMENT`, 청구 자동수정 `CLAIM_AUTOFIX`·AI 보조 `AI_ASSISTED`는 그 기능이 생길 때)를 남깁니다. 판은 추가만 하고 DB 트리거가 수정·삭제를 막습니다 ([clinical.md](clinical.md#정정철회판고정-구현-결정))
  - 삭제 API는 두지 않고 `ENTERED_IN_ERROR` 상태로 대체합니다. 현행 `DELETE /record/{id}`는 복구할 수 없는 삭제였습니다
  - 추가기재·수정 접속기록은 일반 감사 로그와 분리된 저장소(추가만 가능, 수정 불가)에 둡니다
  - 2026년 보도에 따르면 단순 열람도 접속기록 대상으로 넓히는 개정이 추진 중입니다 (확인 필요). 재설계는 처음부터 조회도 기록합니다 ([conventions.md](conventions.md#감사와-열람-기록))

## 보존

- **근거:** 의료법 제22조제2항, 같은 법 시행규칙 제15조는 기록 종류별 보존기간을 정합니다. 흔히 진료기록부 10년, 처방전 2년, 진단서 등 부본 3년, 환자 명부 5년으로 알려져 있습니다 (확인 필요: 종류별 기간)
- **설계 반영**
  - 보존기간은 코드에 박지 않고 `retention-policies` 참조데이터(종류 → 기간, 기산점)로 둡니다
  - 환자 삭제는 진료 이력이 없을 때만 허용합니다 ([patients.md](patients.md#엔드포인트))
  - 보존기간이 지난 데이터는 정책에 따라 파기 작업(Job)으로 처리하고, 파기 대장을 남깁니다
  - 수납·결제 기록은 지우지 않고 `VOIDED`로 남깁니다 (세무 보존 의무도 함께 고려)

## 전자서명

- **근거:** 의료법 제23조와 관련 유권해석은 전자의무기록 작성 시 전자서명 범위를 다룹니다 (확인 필요: 서명 대상·시점의 세부 요건)
- **설계 반영**
  - 서명은 특정 진료 **버전**에 붙습니다. 서명 후 정정하면 새 버전은 서명 전 상태가 됩니다 ([documents.md](documents.md#전자서명))
  - 서명 완료 처리를 클라이언트에 맡기지 않습니다

## 개인정보 최소 노출

- **근거:** 개인정보 보호법 제24조의2(주민등록번호 처리 제한·암호화), 제23조(민감정보), 개인정보의 안전성 확보조치 기준 (확인 필요: 접속기록 보관 기간 1년/2년 기준)
- **설계 반영**
  - 주민등록번호는 필드 단위로 암호화하고, 응답에는 기본으로 `rrnMasked`만 넣습니다. 원문은 `GET /patients/{id}/rrn` + 사유 헤더로만 줍니다
  - 검색용으로는 주민번호 해시(테넌트별 솔트)를 따로 둡니다. 현행 중복 확인 `POST /patients/check-ssn`의 목적을 해시 비교로 달성합니다
  - 이벤트 payload에 주민번호·진료 본문을 넣지 않습니다 ([events.md](events.md#형식))
  - 엑셀 내보내기는 사유 헤더 + Job + 감사 기록입니다. 현행처럼 클라이언트가 다운로드 기록을 따로 보내는 방식은 우회할 수 있습니다
  - 화면 설정 "주민번호 뒷자리 표시"는 응답 마스킹 수준을 바꾸는 서버 설정입니다. 클라이언트가 가리는 방식이 아닙니다

## 오프라인 캐시

- 오프라인 접수·수납을 위해 병원 PC(엣지)에 환자 표시 정보를 둡니다 ([offline.md](offline.md#엣지-캐시)). 개인정보의 안전성 확보조치 기준에 맞춰 기기 키로 암호화하고, 주민번호 원문·해시와 진료 본문은 두지 않습니다
- 오프라인 중 조회·쓰기도 접속기록을 엣지에 남기고 복구 후 서버 감사 로그로 올립니다. 접속기록에 빈 구간이 생기지 않게 하기 위해서입니다
- 오프라인에서 작성하지 못한 진료기록은 복구 후 입력하며, 진료 시각(`serviceAt`)과 입력 시각이 함께 남습니다 (사후 기재 허용 범위는 확인 필요)

## 권한 범위

- **근거:** 의료법 제21조(기록 열람 등)
- **설계 반영**
  - 모든 진료 데이터 접근에 권한과 `scope`(`ALL`/`OWN`)를 서버가 강제합니다
  - 진료기록 작성·처방은 면허 유형으로 한 번 더 제한합니다 ([identity-access.md](identity-access.md#권한-모델))
  - 현행처럼 `requiresAuth`가 빠진 라우트(`/canvas`, `/treatment/repeat-results`)가 진료 데이터를 그리는 일은 서버 인가로 막힙니다

## 광고성 정보 전송

- **근거:** 정보통신망법 제50조
  - 광고성 정보는 사전 수신 동의가 필요하고, 수신거부·동의 철회 후에는 보낼 수 없습니다
  - 오후 9시부터 다음 날 오전 8시까지는 별도 사전 동의가 필요합니다 (제50조제3항)
  - 광고 표시와 수신거부 방법 등을 메시지에 밝혀야 합니다 (제50조제4항, 시행령). 실무에서는 `(광고)` 소괄호 표기가 요구됩니다
- **설계 반영**
  - 환자 동의는 Patients가 단일 출처로 갖고 이력을 남깁니다 ([patients.md](patients.md#동의)). 환자가 아닌 번호의 수신거부(080, 일괄 등록)는 CRM의 번호 단위 `Suppression`에 두고, 발송 시 둘 다 검사합니다 ([crm.md](crm.md#동의와-수신거부))
  - 야간 시간대는 서버 정책값(기본 21:00–08:00)이고, 야간 별도 동의(`MARKETING_NIGHT`)가 없는 수신자는 그 시간대 발송에서 제외합니다. 현행 클라이언트 상수 20:30/20:50은 법정 시간보다 보수적이지만 서로 다르고 서버가 강제하지 않았습니다
  - 법정 표기는 서버가 최종 본문에 붙입니다 ([crm.md](crm.md#엔드포인트-1))
  - 동의 `UNDECIDED`는 광고 발송에서 제외합니다
  - 의료광고는 의료법상 별도 규제(제56조 등)가 있습니다. 콘텐츠 기능을 확장할 때 검토가 필요합니다

## AI 보조

- AI가 만든 진료기록 초안은 의사가 명시적으로 반영(`:apply`)해야 기록이 되고, 버전 이력에 `source: AI_ASSISTED`가 남습니다
- 녹음 원본의 보존 기간과 외부 모델 전송 여부는 테넌트 동의(`TermsAgreement`)와 개인정보 처리방침에 맞춰야 합니다 (정책 결정 필요, [review.md](review.md#결정-필요))

## 외부 기관 연동 자격

- 공단 인증서(.der/.key)와 비밀번호를 서버에 맡기는 현행 구조는 유지하되, 테넌트별 비밀 저장소(KMS)에 두고 사용 기록을 남깁니다
- 심평원 청구 프로그램은 PC 설치형이라 데스크톱 에이전트가 필요합니다 ([claims.md](claims.md#데스크톱-에이전트))
