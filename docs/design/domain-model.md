# 도메인 모델: 커맨드·애그리거트·이벤트·뷰·정책

이 문서는 각 도메인 문서가 정한 업무를 다섯 가지 구성 요소로 다시 나눕니다. 구성 요소는 커맨드, 애그리거트, 이벤트, 뷰, 정책입니다. [Alchemy Domain](https://alchemy.run/domain/what-is-ddd/)이 쓰는 구조를 따르고, 라이브러리는 쓰지 않습니다([D10](review.md#결정-필요)). 이 문서가 새로 정하는 것은 **어떤 커맨드가 어떤 애그리거트를 바꾸고, 다른 애그리거트에 미치는 영향을 어떤 방식으로 전하는가**입니다. 리소스 필드, 상태 전이표, 오류 코드는 각 도메인 문서에 그대로 둡니다.

## 구성 요소

| 구성 요소 | 뜻 | hemr에서의 형태 |
|---|---|---|
| **커맨드** | 도메인에 바꿔 달라는 요청입니다. 명령형으로 이름 짓고, 거부될 수 있으므로 거부 사유를 선언합니다 | `POST /{resource}/{id}:{command}` 하나([conventions.md](conventions.md#커맨드)). 입력은 Schema, 거부는 오류 코드입니다 |
| **애그리거트** | 함께 지켜야 하는 규칙(불변식)과 그 규칙이 필요로 하는 상태의 묶음입니다. 한 번에 커맨드 하나를 처리하는 일관성 경계입니다 | 상태를 저장하는 테이블 한 행(과 하위 행)입니다. 판정은 순수 함수 `decide`입니다(아래) |
| **이벤트** | 이미 일어난 일의 기록입니다. 과거형으로 이름 짓고, 거부하거나 되돌릴 수 없습니다. 바로잡을 때는 새 이벤트를 남깁니다 | outbox 행입니다([events.md](events.md)). 상태와 같은 트랜잭션에 씁니다 |
| **뷰** | 화면이나 다른 모듈이 읽는 모양입니다 | 읽을 때 테이블에서 계산합니다. 결과적 일관성이 아니라 읽는 순간의 상태입니다(아래) |
| **정책** | 이벤트를 받아 할지 말지 정하고, 커맨드를 보내거나 바깥 시스템을 부르는 규칙입니다. 이미 일어난 일을 거부할 수 없습니다 | outbox 소비자입니다. 최소 1회 전달이므로 멱등이어야 합니다 |

정책 외에 두 가지를 더 씁니다.

- **사가:** 여러 단계로 이어지는 작업에 씁니다. 각 단계는 다른 애그리거트이거나 바깥 시스템이고, 뒤 단계가 실패하면 앞 단계를 되돌립니다. 외부 기관 연동 `Job`([conventions.md](conventions.md#비동기-작업))이 사가의 진행 상태를 담습니다
- **예약 커맨드:** 시각이 되면 서버가 스스로 보내는 커맨드입니다. 예약 부도, 패키지 만료, 시술 타이머 만료가 여기에 해당합니다. 지금은 주기적으로 대상을 훑는 작업이 보냅니다

### 애그리거트의 판정 함수

```ts
decide(state, command, context) → { state, events } | 거부
```

- 순수 함수입니다. Effect·저장소·권한을 모릅니다. 시각·행위자·테넌트와, 서비스가 미리 읽어 둔 사실(`hasClinicalData`, 지난 날짜 여부)은 `context`로 받습니다
- 커맨드 처리기(서비스)는 **읽기 → 권한 → `decide` → 저장(상태 + 이벤트, 한 트랜잭션)** 만 합니다
- **`evolve`(이벤트 → 상태)는 두지 않습니다.** hemr는 상태를 저장합니다. 이벤트는 화면이 반응할 최소 필드만 담고, 민감 정보는 넣지 않습니다. 그래서 이벤트로 상태를 다시 만들 수 없습니다
  - 이 선택으로 잃는 것은 이력에서 상태를 다시 만들거나 새 정보를 끌어내는 능력입니다. "왜 이 상태인가"에 대한 답은 진료기록 판·정정 이력과 지우지 않는 outbox 행이 맡습니다
  - 되돌릴 조건: 이력에서 새 정보를 끌어내야 하는 애그리거트가 생기면 [D10](review.md#결정-필요)의 다시 볼 조건에 해당합니다

### 뷰는 읽을 때 계산합니다

Alchemy의 뷰는 이벤트를 접어 만든 읽기 모델이라 애그리거트보다 조금 늦습니다. hemr는 같은 SQLite에서 애그리거트 테이블을 읽어 계산하므로 늦지 않습니다. 접수 화면처럼 방금 쓴 것을 바로 읽어야 하는 곳이 많아 이 방식을 기본으로 둡니다.

- 계산이 무거워지면 그 뷰만 별도 테이블(프로젝션)로 만듭니다. 그때 갱신은 정책이 맡고, 결과적 일관성이 됩니다
- 시재는 좋은 예입니다. 마감 뒤 현금 원장이 바뀌어 `REOPENED`(`CHANGED_AFTER_CLOSE`)가 되는 것을, 수납·환불이 시재를 고치는 방식으로 하지 않습니다. 마감할 때 남긴 원장 지문과 지금 원장을 읽을 때 비교합니다([cash-drawers.ts](../../src/modules/front-desk/cash-drawers/cash-drawers.ts)). 애그리거트 사이에 쓰기가 생기지 않습니다

## 일관성 규칙

1. **커맨드 하나는 일관성 경계 하나를 바꿉니다.** 기본 경계는 애그리거트 하나입니다
2. **두 애그리거트에 걸친 불변식이 있을 때만 경계를 묶습니다.** 묶은 경계는 아래 [묶은 경계](#묶은-경계) 표에 올리고, 어떤 불변식 때문인지 적습니다. 묶은 경계의 `decide`는 그 애그리거트들을 함께 받습니다. 예: `decideCheckout(visit, payments, prepaidAccounts, quote, context)`
3. **나머지 영향은 정책으로 전합니다.** 받는 쪽 애그리거트가 자기 `decide`로 판정합니다. 받는 쪽이 거부하면 정책은 그 사실을 기록하고 멈춥니다. 보낸 쪽 커맨드를 되돌리지 않습니다
4. **다른 컨텍스트의 애그리거트는 정책으로만 바꿉니다.** 묶은 경계가 컨텍스트를 넘는 것은 연쇄 취소 하나뿐이고, 예외로 표에 적습니다

설계 원칙 2("업무 하나 = 요청 하나 = 트랜잭션 하나")는 2번으로 좁아집니다. 지금 한 트랜잭션에서 하는 일 중 불변식이 요구하지 않는 것은 정책으로 옮깁니다. 옮기면 응답 모양이나 실패했을 때의 동작이 바뀌는 것은 [결정](#결정)에 따로 적었습니다.

## 애그리거트

키가 같은 행 하나가 인스턴스 하나입니다. 불변식은 그 애그리거트가 혼자 지키는 것만 적습니다.

### Patients

| 애그리거트 | 키 | 불변식 | 커맨드 |
|---|---|---|---|
| Patient | `patientId` | 테넌트 안에서 차트번호와 주민등록번호가 겹치지 않음(유니크 제약). `MERGED`·`DELETED`는 바꿀 수 없음 | 등록, 수정, 동의 기록, 병합 |
| PackageContract | `contractId` | 쓴 횟수·금액이 총량을 넘지 않음. `ACTIVE`일 때만 사용. 재개 조건 | 사용, 사용 취소·복원, 해지, 재개, 연장, 만료(예약 커맨드) |
| PrepaidAccount | `patientId` + `kind` | 잔액이 0보다 작아지지 않음. 계열별 환불 수단 제약 | 충전, 사용, 환불, 거래 취소 |

### Front Desk

| 애그리거트 | 키 | 불변식 | 커맨드 |
|---|---|---|---|
| Appointment | `appointmentId` | 상태 전이표. 한 셀의 수용 한도(경고) | 등록, 변경, 취소, 도착, 부도(예약 커맨드) |
| Visit | `visitId` | 상태 전이표. 지난 날짜는 진료 흐름 커맨드를 받지 않음. 진료 데이터가 있으면 연쇄 없이 취소하지 않음 | 접수, 진료 시작, 대기로, 수납으로, 다시 열기, 취소, 보험구분 변경 |
| Payment | `paymentId` | 영수증 하나에만 적용. 환불 합이 결제액을 넘지 않음. 수단별 환불 제약 | 기록(`UNAPPLIED`), 적용, 환불 |
| Receipt | `receiptId` | 금액은 서버 계산이고 결산 결과와 맞음. `VOIDED`는 바꿀 수 없음 | 수납(묶음), 취소, 정정 |
| CashDrawer | 병원 + 날짜 | 하루 한 번 개시. `OPEN`·`REOPENED`일 때만 마감과 지출 | 개시, 마감, 다시 열기 |
| Expense | `expenseId` | 그날 시재가 열려 있을 때만 기록·삭제 | 기록, 삭제 |

### Clinical

| 애그리거트 | 키 | 불변식 | 커맨드 |
|---|---|---|---|
| Encounter | `encounterId` | 상태 전이표. 완료 후에는 정정만 가능하고 판이 남음. 고정된 기록은 바꾸지 않음. 완료 검증(중복 진찰료, 보험구분, 첩약 시범사업) | 초안 저장, 완료, 정정, 철회, 고정, 고정 풀기 |
| AmendmentProposal | `proposalId` | `PENDING`일 때만 반영·버림 | 제안, 반영(묶음), 버림 |
| TreatmentSession | `visitId` | 같은 베드의 만료 시술은 다음 시술을 시작할 때 함께 완료(정책 설정). 순서가 내원 안에서 겹치지 않음 | 시술 더하기·지우기·순서 바꾸기, 시작, 완료, 타이머 다시 시작, 일괄 시작·완료, 타이머 만료(예약 커맨드) |

**시술은 내원 단위로 묶습니다([M4](#결정)).** 지금은 시술(`Procedure`) 하나가 애그리거트이고 버전도 시술마다 있습니다. 하지만 일괄 시작·완료, 순서 바꾸기, 만료 시술 자동 완료는 모두 한 내원의 시술 여럿을 함께 봅니다. 불변식이 내원 단위이므로 애그리거트도 내원 단위입니다. 대가로 두 직원이 한 환자의 다른 시술을 동시에 누르면 한쪽이 버전 충돌을 받습니다.

## 커맨드와 영향

굵게 쓴 것이 커맨드가 바꾸는 경계입니다. 오른쪽은 그 밖에 생기는 일과, 그 일을 무엇이 맡는지입니다.

| 커맨드 | 바꾸는 경계 | 그 밖의 영향 | 지금 | 이 설계 |
|---|---|---|---|---|
| 접수 `visits:check-in` | **Visit** | 빈 진료 초안 생성 | 같은 트랜잭션 | 정책 `visit.checked_in` → 진료 초안 생성 (M1) |
| | | 예약 `ARRIVED` | 미구현 | 정책 `visit.checked_in` → 예약 도착 |
| | | 신환 생성·자격 정보 갱신 | 미구현 | 접수 전에 환자 등록·수정 요청을 따로 보냄 (M3) |
| 진료 흐름 `:start-treatment` 등 | **Visit** | 베드 배정은 내원 속성 | | |
| 보험구분 변경 | **Visit** | 맞지 않는 처방 라인 표시, 완료된 진료면 정정 제안 | 미구현 | 정책 `visit.coverage_changed` → 정정 제안 |
| 수납 `visits:checkout` | **묶음: Receipt + Payment + PrepaidAccount + Visit** | 패키지 판매분의 계약 생성 | 미구현 | 정책 `receipt.created` → 계약 생성 |
| | | 처방 라인 금액 확정 | 견적(`quoteId`)으로 검증 | 묶음에 넣지 않음. 견적이 낡으면 409 |
| 수납 취소·정정, 환불 | **묶음: Receipt + Payment + PrepaidAccount** | 시재 원장 변경 | 읽을 때 계산 | 뷰 |
| 내원 취소(연쇄 아님) | **Visit** | 내용 없는 진료 초안 철회 | 같은 트랜잭션 | 정책 `visit.status_changed(CANCELED)` → 진료 철회 (M5) |
| 내원 연쇄 취소 | **묶음(컨텍스트를 넘는 예외)** | 진료 철회, 수납 취소, 패키지·선수금 복원, 시술·탕전 취소, 청구 제외 | 같은 트랜잭션(일부 미구현) | 묶음 유지([D3](review.md#결정-필요)) |
| 진료 완료 `encounters:complete` | **묶음: Encounter + PackageContract** | 내원을 `nextVisitStatus`로 이동 | 같은 트랜잭션 | 정책 `encounter.completed` → 내원 이동 (M2) |
| | | 진행 중 시술 종료 | 같은 트랜잭션 | 정책 `encounter.completed` → 시술 종료 |
| | | 추나 심평원 제출 작업 | 미구현 | 정책 → 사가(`Job`) |
| 정정 제안 반영 | **묶음: AmendmentProposal + Encounter** | | 같은 트랜잭션 | 그대로 |
| 시술 커맨드 | **TreatmentSession** (M4, 지금은 Procedure) | | | |
| 시재 개시·마감·다시 열기 | **CashDrawer** | | | |
| 지출 기록·삭제 | **Expense** | 그날 시재가 열렸는지 읽음 | | 읽기만 하므로 묶지 않음 |

## 묶은 경계

| 묶음 | 불변식 | 묶지 않으면 생기는 일 |
|---|---|---|
| 수납: Receipt + Payment + PrepaidAccount + Visit | 결제는 영수증 하나에만 적용되고 선수금 잔액은 0 밑으로 내려가지 않습니다. 영수증이 있는 내원은 `COMPLETED`이고, 취소된 내원에는 영수증이 생기지 않습니다 | 같은 결제나 선수금을 두 번 쓸 수 있습니다. 동시에 취소와 수납이 들어오면 취소된 내원에 돈이 남습니다 |
| 수납 취소·정정, 환불: Receipt + Payment + PrepaidAccount | 무효인 영수증의 결제는 환불되었거나 다시 미적용입니다. 선수금 사용이 복원됩니다 | 돈과 기록이 어긋납니다 |
| 진료 완료: Encounter + PackageContract | 처방 라인의 패키지 사용이 계약의 남은 횟수·금액을 넘지 않습니다 | 패키지를 넘게 쓴 진료가 완료됩니다 |
| 정정 제안 반영: AmendmentProposal + Encounter | `APPLIED`인 제안은 그 내용의 정정 판이 있습니다 | 반영했다는 제안이 있는데 정정은 없습니다 |
| 연쇄 취소(예외) | D3: 취소는 전부 되거나 전부 안 됩니다. 막히는 경우는 `blockers`로 미리 알립니다 | 일부만 취소된 내원이 남습니다 |

연쇄 취소는 컨텍스트 다섯 곳(Front Desk, Clinical, Patients, Herbal Pharmacy, Claims)의 애그리거트를 한 트랜잭션에서 바꿉니다. 모듈러 모놀리스 안이라 가능한 선택입니다. **되돌릴 조건:** 연쇄 취소가 닿는 컨텍스트 하나라도 따로 배포하게 되면, 연쇄 취소는 사가가 됩니다. 단계마다 되돌리는 동작이 있어야 하고, `dryRun`의 `blockers`는 사가 시작 전 검사가 됩니다.

## 이벤트

이벤트 목록은 [events.md](events.md#이벤트-목록)와 각 도메인 문서가 단일 출처입니다. 이 구조에서 덧붙이는 규칙만 적습니다.

- 이벤트는 그것을 낸 애그리거트의 `decide`가 만듭니다. 서비스 코드에서 `domainEvent(`를 직접 부르지 않습니다
- 정책이 판단에 쓰는 필드는 payload에 넣습니다. 예: `encounter.completed`에 `nextVisitStatus`가 있어야 내원 이동 정책이 동작합니다. 민감 정보는 여전히 넣지 않고, 필요하면 정책이 애그리거트를 읽습니다
- 정책이 다른 애그리거트에 보낸 커맨드가 낸 이벤트는 처음 이벤트의 `correlationId`를 이어받습니다. 연쇄 취소에서 이미 쓰는 규칙([front-desk.md](front-desk.md#연쇄-취소))을 정책 전체로 넓힙니다

## 뷰

| 뷰 | 키 | 읽는 애그리거트 | 지금 |
|---|---|---|---|
| 접수 목록 | 병원 + 날짜 | Visit, Encounter(`encounterStatus`), Receipt(`balance`), PrepaidAccount, PackageContract | 일부 파생 필드만 |
| 치료실 보드 | 병원 + 날짜 | Visit(베드), Procedure, 서버 시각 | `GET /treatment-rooms/board` |
| 시재 현금 흐름 | 병원 + 날짜 | Payment(현금), PrepaidAccount 충전(현금), Expense, CashDrawer | 읽을 때 계산 |
| 일자 현황 | 병원 + 날짜 | Appointment, Visit, Receipt, Payment | 미구현 |
| 예약 가용성 | 병원 + 날짜 + 의사 | Appointment, 일정 차단, Catalog 진료시간 | 미구현 |
| 허용 동작(`allowedActions`) | 애그리거트마다 | 그 애그리거트 | 내원·진료 |

키가 없는 조회는 Alchemy 용어로 쿼리(query)입니다. 환자 검색(이름·초성·차트번호·전화번호 뒷자리)과 수납 목록이 여기에 해당합니다. 지금처럼 테이블을 읽습니다.

허용 동작은 그 애그리거트의 `decide`를 커맨드마다 시험해 보는 것과 같아야 합니다. 같은 전이표를 따로 읽지 않고, 시험 결과로 만들면 둘이 어긋날 수 없습니다.

## 정책

| 정책 | 받는 이벤트 | 보내는 커맨드 | 받는 쪽이 거부하면 | 상태 |
|---|---|---|---|---|
| 진료 초안 만들기 | `visit.checked_in` | 진료 초안 생성 | 기록만 합니다. 의사가 차트를 열 때 만듭니다 | 옮길 것 (M1) |
| 예약 도착 | `visit.checked_in` (`appointmentId` 있음) | 예약 도착 | 기록만 합니다(이미 취소된 예약 등) | 예약 구현 때 |
| 빈 초안 철회 | `visit.status_changed` (`CANCELED`) | 진료 철회 | 기록만 합니다 | 옮길 것 (M5) |
| 진료 후 내원 이동 | `encounter.completed` | 내원 진료 흐름 커맨드 | 기록만 합니다. 내원 상태는 데스크가 옮깁니다 | 옮길 것 (M2) |
| 진료 후 시술 종료 | `encounter.completed` (`WAITING`·`AWAITING_PAYMENT`) | 시술 일괄 완료 | 기록만 합니다 | 옮길 것 |
| 보험구분 정정 제안 | `visit.coverage_changed` | 정정 제안 생성 | — | 구현 때 |
| 패키지 계약 생성 | `receipt.created` (패키지 판매분 있음) | 계약 생성 | 실패를 남기고 재시도합니다. 돈은 이미 받았습니다 | 구현 때 |
| 추나 자동 제출 | `encounter.completed` | 심평원 제출 사가 시작 | — | Claims 때 |
| CRM 연락 작업 | `encounter.completed`, `visit.*`, `appointment.*` | 연락 작업 생성 | — | CRM 때 |

정책은 [events.md](events.md#모듈-간-서버-내부)의 규칙을 따릅니다. 소비자마다 마지막으로 처리한 `seq`를 저장하고, 이벤트 `id`로 중복을 거릅니다. 첫 정책을 붙일 때 이 저장을 만듭니다. 지금 버스 구독자는 로그(`EventLog`) 하나라 아직 없습니다.

## 코드 배치

저장소는 이미 종류를 접미사로 붙입니다(`visits.api.ts`, `visits.http.ts`, `*.types.ts`). 같은 방식으로 이렇게 둡니다.

| 파일 | 담는 것 |
|---|---|
| `visit.aggregate.ts` | 상태 Schema, 커맨드 입력, 거부, `decide`, 허용 동작 |
| `checkout.aggregate.ts` | 묶은 경계의 `decide`. 이름은 커맨드를 따릅니다 |
| `visits.ts` | 커맨드 처리기(서비스): 읽기 → 권한 → `decide` → 저장 |
| `visit-board.view.ts` | 뷰 계산 |
| `encounter-draft.policy.ts` | 정책: 받는 이벤트, 판단, 보내는 커맨드 |
| `visits.api.ts`, `visits.http.ts` | 그대로 |

규칙 계산 모듈(`docs/reference/rules/`에 규칙 문서가 있는 것)은 이미 순수 함수이므로 `decide`가 부르는 쪽으로 둡니다. 파일 이름은 바꾸지 않습니다.

## 단계

1. **내원 시범**([#66](https://github.com/cbcruk/hemr/issues/66)): `visit.aggregate.ts`로 옮기고 동작은 바꾸지 않습니다. 이 문서의 규약을 확정합니다
2. **나머지 애그리거트**([#67](https://github.com/cbcruk/hemr/issues/67)): 묶은 경계 표의 묶음부터 `decide`로 옮깁니다. 동작은 바꾸지 않습니다
3. **정책 기반**([#68](https://github.com/cbcruk/hemr/issues/68)): 소비자별 `seq` 저장과 정책 실행기를 만듭니다. 첫 정책은 동작이 바뀌지 않는 것으로 고릅니다(진료 후 시술 종료처럼 응답에 실리지 않는 것)
4. **트랜잭션에서 정책으로 옮기기:** 아래 결정대로 하나씩 옮깁니다. 응답 모양이 바뀌는 것(M1·M2)은 OpenAPI와 도메인 문서를 함께 고칩니다
5. **시술 애그리거트 넓히기(M4)**
